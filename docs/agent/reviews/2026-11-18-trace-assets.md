# 跨关卡 trace 抽样：哪些内容可以沉淀为资产

分析日期：2026-11-18。目标：根据真实历史记录判断复盘的可用产物，不修改运行逻辑或攻略策略。

## 样本与统计口径

完整流式读取以下 7 个 trace 文件，按关卡变化或 level_time 回退拆成 17 段，覆盖 UI 2-2、2-4、3-2、3-3、4-1、4-2、4-3、4-4、4-5 共 9 关。8 段观察到倒计时剩 1 秒，作为“接近完整局”；其余是中断/短片段，不比较最终成绩。重点核对下文案例，同时读取相关 voice 的调用与 ack。

- `runs/trace-20261115-133954.jsonl`
- `runs/trace-20261115-005937.jsonl`
- `runs/trace-20261111-233924.jsonl`
- `runs/trace-20261115-223025.jsonl`
- `runs/trace-20261115-214745.jsonl`
- `runs/trace-20261118-222952.jsonl`
- `runs/trace-20261118-224142.jsonl`

统计用 state.level_time 的正增量对 exec.task 加权，同一时钟快照不重复累计；排除 paused、非 level、无倒计时、倒计时为零的帧，跨记录超过 1 秒的间隔不累计。相邻区间按后一帧任务归属，存在约一个状态帧的边界误差。旧日志可能没有标全暂停；开局倒计时冻结但允许操作的时间仍计入观察时长。故这里的“执行占用”是观察区间内任务身份的占用，包含走路、等待、清手等，不等于有效动作耗时，也不统一等于游戏倒计时消耗。没有用行数乘 50ms。

送达数属于双方共同结果，不归因给 AI。不同日期即使插件版本相同，也不代表 Python、提示词、玩家操作相同，不能做因果性的版本成绩对比。历史现象不代表当前未提交代码仍有同样问题。以下策略建议均未经过新实机验证。

## 1. 4-4：口头分工与实际工具设置不一致

证据：`voice-20261118-224142.jsonl:5-10`；`trace-20261118-224142.jsonl:70`。

- 模型说“你切菜，我负责下锅和上菜，切好递过来就行”。
- 同一回合实际设置：玩家 `chop`；AI `cook`、`prepare:NuggetChicken`、`prepare:Potato`，工具 ack 成功。
- trace 行 70 中 AI 执行 FetchToBoard 鸡肉，候选 pref=0。这里取料上板并未被这份分工交给玩家。
- 玩家随后说“你负责鸡肉我负责。”（ASR 文本不完整，不能把它当完整人类原话）；模型将鸡肉 prepare 留给 AI、土豆 prepare 改给玩家。
- 行 221 中土豆 FetchToBoard 的 pref=-6，证明分工确实能影响 planner 的一个具体环节，并非只影响说话。
- 本段约 55.0 秒：FetchToBoard 24.0 秒，FillCooker 11.2 秒，没有执行任务身份约 11.0 秒；中断时 0 送达。不能据此判断该分工整局一定更差。

可沉淀：一组“自然语言协作意图 → 工具 assignments → ack → 对应任务 pref”的一致性案例。下次决定谁负责一类食材时，明确区分取料上板、切配、下锅，播报反映实际设置；若期望玩家包办备料，不能仅设置 chop。

落地：现有 set_division 已有控制入口；提示词示例、工具参数校验/结果说明、离线对话评测均可用。不能固化为“4-4 永远玩家切、AI 炸”，样本不支持最优分工结论。

补充：`voice-20261118-222952.jsonl:7-10` 中 prepare 未带 item 被部分拒绝，模型补齐两个 item 后成功。这是值得保留的工具纠错成功案例。

## 2. 3-3：玩家明确调整被布局复核覆盖

证据：`voice-20261115-133954.jsonl:120-135`；对应 trace 行 3018、3400。

- 13:46:11（北京时间）玩家说“烤箱你也可以碰”。
- 13:46:12 工具成功将 chop/cook 设为 both，随后实际播报“谁近谁干”。
- 13:46:36 的 layout_review 又把 chop/cook 全分给玩家。工具 ack 还附带警告：玩家现在够不着下锅站点，可能只是暂时挡路。
- 后续 trace 的分工也保持 player chop/cook。这证明发生了覆盖；仅凭这些记录不能断言当时绝对不应调整，还需核对完整分区与可达性。
- 该局约 239.8 秒，FetchToBoard 84.6 秒、Chop 35.4 秒、Reposition 18.6 秒，双方合计送达 5 单。不能将所有未出餐时间归因于分工。

可沉淀：玩家临场修正的来源、时间、后续被哪个事件覆盖；临时隔断引起的适配应有恢复条件，而非无条件写成永久分工。

落地：现有 layout_review/set_division 的回放案例；进一步可以给分工加来源与临时覆盖/恢复语义，由主循环应用，保持唯一写入入口。只往攻略加一句“尊重玩家”不足以保证生效。

## 3. 3-2：工具拒绝不能当成游戏机制事实

证据：`voice-20261115-133954.jsonl:6-9`；trace 行 2 起为 `Wizard_5_5_2P`、UI 3-2，快照包含煎锅和汉堡任务。

- 模型请求 player cook:Meat。
- ack 部分拒绝，原因为“meat 不需要下锅”；其余切菜分工接受。
- 模型随后把该错误信息当成事实复述：“下锅那条被拒了（肉不需要下锅），不影响大局”。
- 该段后来实际出现 FriedMeat 的取熟料、组装任务。故至少不能从这次工具拒绝推导出“本关肉不用煎”。拒绝究竟来自生料/熟料节点归一还是目录判定，需要单独排查，本文未确定代码根因。

可沉淀：带关卡、配方节点、被拒参数和成功等价调用的工具兼容性案例；遇到工具错误时查配方与 ack，而非把错误写成永久攻略。

落地：工具层归一化与错误文案回归；模型可先用已支持的粗粒度 cook 分工或查询状态再修正，但不能假定任意 fallback 都成功。

## 4. 4-2：传送带接盘是显著的执行成本

证据：`trace-20261115-005937.jsonl:3237-7724`，其中行 4085、6667 为接盘片段。

约 239.8 秒，双方送达 6 单：

| 执行任务身份 | 占用秒数 |
|---|---:|
| FetchConveyorPlate | 51.2 |
| SendAcross | 33.6 |
| WashPlate | 19.6 |
| PlaceCleanPlate | 11.0 |
| 无任务身份 | 27.6 |

接盘+送件+洗盘+放净盘共约 115.4 秒，占 48%；其中包含合理物流，不能全算浪费。一个接盘连续片段约 11.8 秒（level_time 187.315–198.918），多处记录 lost_stance、no clear floor 等执行问题。另一局 `trace-20261111-233924.jsonl:2947-7435` 同关接近完整段送达 8 单，接盘占 33.2 秒；配置/玩家不同，不能声称少接盘就多送两单。

可沉淀：传送带接盘的成功耗时分布、超时片段、盘子身份与轨迹、失败站位，以及交接时机的候选策略。上游放盘速度是否超过接收能力，需逐盘跟踪确认，不能只凭累计时间判断。

落地：执行回归 fixture、接盘超时后的重新站位/恢复机制，以及基于可接收状态的交接提示。只更换切菜分工无法保证改善。

## 5. 2-4：反复灭火比“切什么料”更值得优先复盘

证据：`trace-20261115-223025.jsonl:2-2054` 和 `:2057-4213`。

两次中断尝试中，分别观察约 195.4 秒、176.6 秒；Extinguish 任务身份占 48.2 秒、51.8 秒（约 25%、29%）。第二次最后一个连续灭火片段约 33.6 秒，开始行 3940。该帧确有米饭锅 onFire，并非单靠任务名字猜发生火灾；另有蘑菇已熟。两段都仅观察到 2 次送达，未到结算。

首段开局玩家负责 cook，第二段开局分工为空，voice 中有 division 的 LLM 超时。两种条件下都出现长灭火，不能把问题简单归结为某套分工。

可沉淀：熟锅→起火→取灭火器/清手/走位→灭火完成的整条事件链，区分“预防没做好”和“已经起火但救援迟迟没完成”。目前的聚合不足以精确分摊两者。

落地：先构造取灭火器/移动/灭火的失败回归；再验证熟锅提前救援和就近处理策略。备料技巧不能直接解决灭火执行卡住。

## 6. 4-1：可沉淀的是运输预算，不能把低分都归因于等红灯

证据：`trace-20261115-005937.jsonl:2-3231`。

约 179.8 秒、双方 5 单。DeliverPlate 占 36.6 秒、WashPlate 26.4 秒；traffic.wait 标记累计约 14.8 秒。第三次送达 level_time 75.230，第四次 168.433，间隔约 93.2 秒。

整个观察窗口的显式等车时间仍小于这次出餐间隔，因而“主要因为一直等车”的解释证据不足。还须沿订单串起备料、洗盘、装盘、移动和恢复。等车标记可能不覆盖全部交通影响，因此也不能据此排除交通问题。

可沉淀：端盘与洗盘的真实运输耗时、跨街次数与等待位置、同单多阶段的时间线，用于 ETA 校准和选择下一次交接试验。不能从一局推出应把送餐永久交给某个人。

## 7. 其他可直接沉淀的内容与边界

- **关卡身份事实**：本次真实帧明确给出 `Wizard_5_5_2P → UI 3-2`、`Balloon_2_3_2P → UI 2-2`、`Mine_5_3_2P → UI 4-4`。可以作为索引核验依据，避免按内部资产名数字误读 UI 编号；人数后缀、版本仍保留。
- **指令可执行性**：`voice-20261118-222952.jsonl:18-25` 中玩家要求洗碗，工具因洗碗池不可达/被占用拒绝，模型改口解释；该轮实际 first_audio 是修正后的说明。应该保留这种成功反馈链，而非把它记成模型拒绝配合。是否真不可达仍需几何核验。
- **前置问题优先**：4-5 短段里无任务身份累计约 88.2 秒，远比先研究“最佳切配分工”更值得定位。但该段不完整，本文未深入核验，不能生成该关永久策略。
- **2-2 样本**：约 115.2 秒中熟料取盘任务占 33.6 秒，送餐任务占 18.4 秒，观察到 1 单送达。只是阶段耗时线索，还不能证明瓶颈是过门、缺盘或任务振荡。

## 资产的最小格式与实施优先级

每条保存：关卡/人数/版本、观察事实、trace/voice 行号、原因假设、可控入口、预期行为变化、验证状态与失效条件。事实与策略假设分开；历史事件不能直接升级为当前代码的已知缺陷。

1. 先做“口头→调用→ack→候选打分→实际执行”的对话/分工案例库。4-4 和 3-3 已有具体证据，现有工具能施加影响。
2. 同时把 4-2 接盘、2-4 灭火沉淀成执行回归片段。这类资产通过改代码改善行为。
3. 有多局可比数据后再维护关卡策略与耗时参数。新策略先试验，标注控制入口；未验证结论不注入下一局的固定攻略。
4. 报告中保留成功修正与不确定结论，防止复盘反复把工具错误或单次偶然结果写成游戏规则。

这次没有验证任何“最佳分工”或预期提分值；已经验证的是：历史记录里存在能映射到工具行为、对话回归、执行回归和关卡事实索引的具体资产。
